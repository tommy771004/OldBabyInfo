## Comments

### 資料來源與範圍

用的是 03 號票 spike 已經找到、但當時是 2024 年 9-10 月的舊資料；這次重新去 hackmd 找到**當下最新一期**（2026 年 7-8 月，正好對上「今天」）的 Funbox G3 與 B4-G3 兩份門市排程表，不是拿舊資料充數。全部 767 筆都是**目前真實在跑的門市賽事場次**：店名、電話、地址、日期、時間、人數上限、報名方式、年齡分組。

**只有 G3 一個層級**——這是誠實的範圍限制，不是偷懶：G3 是門市層級的常態賽事，官方或更高層級（GP／G1／G2）賽事不是透過這套門市合作排程系統辦理，我沒有找到對應的公開資料源。Event schema 完整支援四個層級，只是種子資料目前只覆蓋得到 G3。

**「參賽結果」幾乎全部是 null**——這不是漏做，是誠實反映 03 號票的發現：整個社群一整年只有一場賽事留下完整名次紀錄。`results` 欄位結構就位（`topFour` + `sourceExcerpt`），等 32 號票或未來有真實資料時再填。

### 過程中發現的領域細節：Event Tier ≠ 年齡分組

CSV 裡的「賽制」欄位（「公開 (6歲以上)」／「通常 (6~12歲)」）一開始容易誤認成 Event Tier，實際上是**年齡資格分組**，跟 CONTEXT.md 定義的 Event Tier（GP/G1/G2/G3，代表賽事規模與權重）是完全不同的維度——兩份表格本身都明確標題為「G3比賽」，年齡分組是同一場 G3 賽事底下的子場次區分。Schema 分成 `tier` 與 `ageCategory` 兩個獨立欄位，沒有混在一起。

### 抽取過程：真實資料的雜訊，逐筆處理而非整批放棄

767 筆資料是從約 780 筆原始列逐筆驗證後的結果，過程中發現：
- 報名方式其實有 **5 種**，不是常見的「現場／線上」兩種：電話、皆可（現場或線上皆可）、門市社群（透過店家自己的社群帳號，語意上跟通用線上報名不同，特意分開）。
- 時間格式「9:00」（無前導零）是合法格式，不是錯字，正規化成補零的 `09:00`。
- 少數幾筆（2 筆）是原始資料本身的手誤（日期漏打斜線、時間用句點代替冒號）——這種個案不值得為了一兩筆去猜測修正規則，逐列驗證、跳過、記錄原因，不讓整批資料因為兩三筆壞資料而失敗。

### 執行期驗證

吸取 11 號票的教訓，沒有只看 build 綠燈就結案——用 `next start` 實際送請求，確認 `/events` 與 `/en/events` 都回 200，並直接寫一個暫時性測試繞過 HTTP 層核對 `splitByDate` 的真實數字（459 即將舉行 + 308 已結束 = 767），再用 curl 核對頁面真的渲染出「已結束 (308)」的收合區塊，數字吻合。
