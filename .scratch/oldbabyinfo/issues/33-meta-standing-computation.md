## Comments

03 號票的 spike 實測：現有賽事資料裡，使用率有 1215 筆真實紀錄可用，但全年只有一場賽事留下完整名次（見 ADR-0003 更新）。意味著測試資料集必須把「樣本不足」當成**主要情境**準備，不是邊角案例——上線初期前八強佔比／奪冠次數幾乎每筆都會落在這個分支。

**31 號票的 Event 種子資料再次確認這個現實**：767 筆真實 G3 賽事場次，`results` 全部是 `null`。且 31 號票的種子資料**只有 G3 一個層級**（官方或更高層級賽事沒有對應的公開排程資料源）——這張票設計統計口徑時，「統計期間」與「樣本數」的計算範圍現階段等同於「G3 門市賽事範圍」，不是全賽事層級的完整圖像，這點在畫面文案上也該誠實反映。

---

**這張票只做計算引擎本身，真實資料還沒接上——這是誠實的範圍界線，不是偷工。** 開工前先確認
`Event.results.topFour`（09／31 號票定的 schema）只是一個扁平的 `string[]`，沒有「哪個
玩家用哪組 Combo」的對應關係；ADR-0003 提到的 1215 筆真實配招紀錄活在 hackmd 的獨立試算表
裡，從來沒有被匯入這個 repo 的 schema——把那份試算表轉成結構化資料是另一個尚未存在、也不在
這張票範圍內的資料匯入步驟。因此這張票的產出是一個乾淨的純函式計算引擎
（`src/lib/meta-standing.ts`），輸入是獨立定義的 `ComboAppearance[]`（不直接讀
`Event.results`），測試用手寫固定資料集覆蓋（票面本來就要求「固定的測試資料集」，不是真實
資料），等 32／35 號票之後真的把賽果資料匯入排程完備時，隨時可以接上。

**統計口徑決策（票面明確要求要定義，這裡是具體決定）：**
- **前八強佔比的分母＝這個 Combo 自己的出場次數**（不是全場前八強席次），衡量「這個組合一旦
  被使用，打進前八的機率」，比「這個組合佔全部前八強席次的比例」更貼近玩家關心的問題。
- **使用率的分母＝統計期間內全部 Combo 的總出場次數**——這條刻意跟前八強佔比的分母不同，
  因為兩者衡量的是不同問題（使用率答「大家都在用什麼」，前八強佔比答「用了之後表現如何」），
  硬套同一個分母會讓其中一個指標失真。
- **統計期間＝實際輸入資料裡最早與最晚的賽事日期**，動態算出來，不是寫死的日期範圍或憑空
  宣稱「涵蓋全年」。
- **Sample Size 門檻只套用在「前八強佔比」與「奪冠次數」這兩個依賴該 Combo 自身樣本的欄位，
  不套用在使用率**——因為 ADR-0003 的 spike 明確區分了兩者的資料可信度：使用率有 1215 筆
  真實紀錄撐著，「資料紮實」；前八強佔比與奪冠次數全年只有 n=4，「完全撐不住統計意義」。
  用同一個門檻蓋住兩者，會把明明可信的使用率也一起藏起來，不必要地保守。
- **Combo 同一性判準＝Blade＋Ratchet＋Bit 三個 id 的精確組合**，同一組三個零件即使背後有
  不同 Stat Edition 歷史紀錄也視為同一個 Combo——玩家選的是三個具名零件，不是某個特定歷史
  SKU（呼應 ADR-0007 的 Stat Edition／Mold Batch 拆分決策）。

**「資料不足」不是回傳 0，是回傳一個不同的狀態值。** `top8Rate`／`championCount` 未達門檻時
回傳 `{status: "insufficient_data"}`，不是 `{status: "computed", value: 0}`——避免下游頁面
（34 號票）誤把「資料不足」渲染成「這個組合前八強機率是 0%」這種比沒有資料更糟的錯誤訊息。

**測試：** `meta-standing.test.ts`，8 個測試，涵蓋樣本不足回傳資料不足狀態、樣本足夠時算出
正確比率（用手算數字驗證：10 筆出場、3 冠軍＋3 前八＝60% 前八強率）、使用率不受單一 Combo
自身樣本門檻影響、統計期間動態反映真實輸入日期範圍、空輸入不報錯、依 Combo 分組而非依賽事
分組、Combo 同一性判準的一致性。

**Pipeline：** `npm run typecheck`、`npm run lint`、`npx vitest run`（174/174）、
`npm run build` 全數通過。
