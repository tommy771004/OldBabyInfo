# 11 — 跨語言搜尋

**What to build:** 使用者不論以中文、日文、英文或玩家俗稱搜尋，都能找到正確的 Part——且不受當前介面語言限制。

**Blocked by:** 10

**Status:** ready-for-agent — done, see Comments

這是本站相對於既有聚合站最核心的差異化能力。

- [x] 在 zh-TW 介面下輸入英文或日文名稱皆可命中
- [x] `aliases[]` 全部納入索引，俗稱與常見錯字可命中（範圍受限，見 10 號票 Comments）
- [x] 搜尋在客戶端完成，無伺服器往返

## Comments

10 號票的 `aliases[]` 目前只有 Bit 短代碼（來自官方資料），玩家俗稱／簡稱／常見錯字幾乎沒有——這部分沒有結構化來源，需要人工蒐集（見 10 號票 Comments）。這張票的英文／日文／中文三語搜尋（AC 1）不受影響，因為那三個名稱都齊備；但「俗稱可命中」（AC 2）目前只能覆蓋 Bit 短代碼這一小部分，別誤以為 alias 索引空是這張票的 bug。

### 實作與一個重要的架構修正

`src/lib/parts/search-parts.ts`（純函式，9 個測試）比對 nameEn／nameJa／nameZhTw／aliases，忽略大小寫與空白差異。搜尋框是獨立的 Client Component（`searchable-rows.tsx`），疊加在 12 號票已經做好的伺服器端類型過濾／排序之上——排序連結繼續是純 `<a href>`，不需要 JS 也能動；只有文字搜尋本身需要 JS，這是誠實的取捨，不是疏漏。

**過程中抓到一個 `npm run build` 沒抓到、只有真的用 `next start` 送請求才會暴露的執行期錯誤**：一開始把 `buildQuery`（一個純函式）當 prop 從伺服器元件傳給 Client Component，React Server Components 不允許函式跨這個邊界序列化，正式伺服器模式下直接回 500。`next build` 本身不會觸發這個錯誤（靜態產生階段沒有走到真正的序列化路徑），只有啟動伺服器、真的送一個請求才會炸——這也是我沒有只看 build 綠燈就結案的原因。修法是把 `buildQuery` 抽成獨立模組（`build-query.ts`），伺服器端與客戶端各自 import，不再跨界傳函式。修完後用 `next start` 實際送請求確認 200，並用 curl 核對 169 列（168 零件＋表頭）資料正確渲染。

**一個誠實的驗證缺口**：搜尋框「打字即時過濾、不重新整理頁面」這個互動本身，因為瀏覽器工具（Chrome 擴充功能）連續逾時無回應，沒有在真實瀏覽器裡實際操作驗證過。純函式邏輯（9 個測試）與 React 邏輯本身（`useState`／`onChange`／`useMemo`，標準且低風險的寫法）都沒問題，伺服器渲染的初始畫面也用 curl 驗證過是對的；但「使用者真的打字、畫面真的即時變化」這件事，這次沒有機會用瀏覽器工具眼見為憑。
